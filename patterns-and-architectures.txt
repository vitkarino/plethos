$meta : {

	},
	status : success | error,
}

error $meta structure
$meta : {

		human : Date,

	},

	error : {
		code : string,
		message : string
	}
}

------
requests style

Do not use await or try ... catch in the components. Instead, use .then() and .catch() to handle promises. This allows for better error handling and keeps the component code cleaner.

------
Architecture and patterns
Always when writing code, strictly follow DRY and SOC. Also decide weither component or page you writing is dumb or smart. If it's dumb, it should only receive props and emit events. If it's smart, it can handle its own state and logic. This helps to keep the code organized and maintainable.
Always separate concerns by using MVVM pattern. This means that the Model should handle data and business logic, the View should handle the UI, and the ViewModel should act as a mediator between the Model and the View. This helps to keep the code organized and maintainable.
If you notice that some piece of code inside of page and component is either repeating or is doing more than one thing, consider extracting it to a separate file/component. This helps to keep the code organized and maintainable.

------
BEM Naming: Block__element_modifier
Follow BEM strictly using this convention: Block__element_modifier
Think of it like a parking lot:

Block = a car (a standalone entity: .shopping-list, .nav-bar, .user-card)
Element = a part of the car (.shopping-list__item, .nav-bar__link)
Modifier = a variation of the car (.shopping-list__item_highlighted, .form__input_type_number)

Zebra Pattern
Alternate between Block and Block__element levels when nesting templates.
Each Block is its own "parking lot" — elements belong to their block, not nested inside other elements.
✅ Correct zebra nesting:
shopping-list              ← Block (parking lot 1)
  shopping-list__items     ← Element of shopping-list
    item                   ← Block (parking lot 2) — new block, new context
      item__name           ← Element of item
      item__quantity        ← Element of item

❌ Wrong — element of element:
shopping-list__items__item__name   ← Never nest elements like this
When a "part" becomes complex enough to have its own elements, promote it to a Block.
Naming rules

Blocks: kebab-case (shopping-list, user-card)
Elements: block__element with double underscore (shopping-list__item)
Modifiers: block__element_modifier with single underscore (form__input_type_number)
For block-level modifiers: block_modifier (shopping-list_compact)

Nuxt Development Skill
This skill enforces a disciplined architecture for Nuxt 3/4 projects built on four pillars: MVC separation, BEM naming, OOP class design, and the Adapter pattern. Every piece of generated code must follow these patterns — no exceptions.

TypeScript only. No JavaScript.

Core Architecture: MVC (Model-View-Controller)
Think of it like a restaurant:

Model = the kitchen (business logic, data shapes, rules). Nobody from the dining room walks into the kitchen.
Controller = the waiter (carries requests between kitchen and dining room, orchestrates flow).
View = the dining room (displays the food, takes orders from the customer, hands them to the waiter). Never talks to the kitchen directly.
File structure for a feature
For a feature called ShoppingList:

features/
  shopping-list/
    models/
      ShoppingListItem.ts      ← Model: business logic, data shape
      ShoppingList.ts           ← Model: collection logic, rules
    controllers/
      ShoppingListController.ts ← Controller: orchestrates Model ↔ View
    views/
      ShoppingListUI.ts         ← View: UI state, DOM interaction logic
    ShoppingList.vue            ← Thin template shell (delegates to UI class)
Model — business logic only
Models hold data shape, validation, computed properties, and domain rules.
They know nothing about the UI or network requests.

typescript
// models/ShoppingListItem.ts
export class ShoppingListItem {
  public id: string
  public name: string
  public quantity: number
  public purchased: boolean

  constructor(id: string, name: string, quantity: number) {
    this.id = id
    this.name = name
    this.quantity = quantity
    this.purchased = false
  }

  public markPurchased(): void {
    this.purchased = true
  }

  public isValid(): boolean {
    return this.name.trim().length > 0 && this.quantity > 0
  }
}
Controller — the orchestrator
The Controller talks to the Model and exposes results to the View. Network requests, method calls, and coordination logic live here. Uses .then()/.catch() — never await or try...catch.

typescript
// controllers/ShoppingListController.ts
import { ShoppingListItem } from '../models/ShoppingListItem'

export class ShoppingListController {
  private apiBase: string

  constructor(apiBase: string = '/api/shopping-list') {
    this.apiBase = apiBase
  }

  public fetchItems(
    onSuccess: (items: ShoppingListItem[]) => void,
    onError: (error: string) => void
  ): void {
    fetch(this.apiBase)
      .then((response) => response.json())
      .then((data: Array<{ id: string; name: string; quantity: number }>) => {
        const items = data.map(
          (raw) => new ShoppingListItem(raw.id, raw.name, raw.quantity)
        )
        onSuccess(items)
      })
      .catch((error: Error) => {
        onError(error.message)
      })
  }

  public addItem(
    name: string,
    quantity: number,
    onSuccess: (item: ShoppingListItem) => void,
    onError: (error: string) => void
  ): void {
    fetch(this.apiBase, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ name, quantity }),
    })
      .then((response) => response.json())
      .then((raw: { id: string; name: string; quantity: number }) => {
        onSuccess(new ShoppingListItem(raw.id, raw.name, raw.quantity))
      })
      .catch((error: Error) => {
        onError(error.message)
      })
  }
}
View (UI class) — UI state and interaction logic
The View class manages reactive UI state and delegates complex operations to the Controller. It never imports or instantiates Models directly — everything goes through the Controller.

Use a reactive state object to hold all UI state in one place:

typescript
// views/ShoppingListUI.ts
import { reactive } from 'vue'
import { ShoppingListController } from '../controllers/ShoppingListController'
import type { ShoppingListItem } from '../models/ShoppingListItem'

interface ShoppingListState {
  items: ShoppingListItem[]
  newItemName: string
  newItemQuantity: number
  isLoading: boolean
  error: string | null
}

export class ShoppingListUI {
  public state: ShoppingListState
  private controller: ShoppingListController

  constructor() {
    this.state = reactive<ShoppingListState>({
      items: [],
      newItemName: '',
      newItemQuantity: 1,
      isLoading: false,
      error: null,
    })
    this.controller = new ShoppingListController()
  }

  public loadItems(): void {
    this.state.isLoading = true
    this.state.error = null

    this.controller.fetchItems(
      (items) => {
        this.state.items = items
        this.state.isLoading = false
      },
      (error) => {
        this.state.error = error
        this.state.isLoading = false
      }
    )
  }

  public addItem(): void {
    if (!this.state.newItemName.trim()) return

    this.controller.addItem(
      this.state.newItemName,
      this.state.newItemQuantity,
      (item) => {
        this.state.items.push(item)
        this.state.newItemName = ''
        this.state.newItemQuantity = 1
      },
      (error) => {
        this.state.error = error
      }
    )
  }
}
The .vue template — a thin shell
The .vue file instantiates the UI class and binds to its reactive state. It contains only framework-specific wiring (template syntax, lifecycle hooks via onMounted, etc.). No business logic, no direct API calls, no complex state management.

vue
<script setup lang="ts">
import { onMounted } from 'vue'
import { ShoppingListUI } from './views/ShoppingListUI'

const UI = new ShoppingListUI()

onMounted(() => {
  UI.loadItems()
})
</script>

<template>
  <div class="shopping-list">
    <div v-if="UI.state.isLoading" class="shopping-list__loader">
      Loading...
    </div>

    <div v-if="UI.state.error" class="shopping-list__error">
      {{ UI.state.error }}
    </div>

    <ul class="shopping-list__items">
      <li
        v-for="item in UI.state.items"
        :key="item.id"
        class="shopping-list__item"
      >
        <span class="item__name">{{ item.name }}</span>
        <span class="item__quantity">× {{ item.quantity }}</span>
      </li>
    </ul>

    <div class="shopping-list__form">
      <input
        v-model="UI.state.newItemName"
        class="form__input"
        placeholder="Item name"
      />
      <input
        v-model.number="UI.state.newItemQuantity"
        class="form__input form__input_type_number"
        type="number"
        min="1"
      />
      <button class="form__button" @click="UI.addItem()">Add</button>
    </div>
  </div>
</template>

OOP — Strictly Object-Oriented
All logic lives in classes. No loose functions, no functional-style composition.

Models are classes with methods
Controllers are classes that orchestrate
Views (UI) are classes that hold reactive state
Utility/helper logic → static methods on a class, or a dedicated utility class
typescript
// ✅ Correct
export class DateFormatter {
  public static format(date: Date, pattern: string): string {
    // ...
  }
}

// ❌ Wrong — loose function
export function formatDate(date: Date, pattern: string): string {
  // ...
}

----------
No watch, watchEffect, computed unless absolutely necessary
If you determine one of these is truly needed (rare cases like URL query sync or cross-cutting reactive deps), warn the user explicitly before using it:

⚠️ Using watch here because [specific reason]. Consider whether this reactive dependency can be handled through explicit method calls instead.

Most of the time, explicit method calls on the UI class replace the need for watchers.
No Pinia
State lives in the MVC classes via reactive() objects inside UI classes. No external state management libraries.

---------
Refactoring Checklist
When refactoring existing Nuxt/Vue code to follow this architecture:

Identify business logic in .vue files → extract to Model classes
Identify API calls and orchestration → extract to Controller classes
Identify UI state and interaction logic → extract to View (UI) classes
Leave only framework wiring in .vue files
Rename CSS classes to follow BEM with zebra pattern
Replace loose functions with class methods
Wrap external dependencies with Adapters
Replace await/try...catch with .then()/.catch()
Remove watch/watchEffect/computed where possible — replace with explicit method calls
Remove Pinia stores — migrate state into MVC reactive classes
